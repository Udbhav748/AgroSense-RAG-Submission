# Not Applicable

Some evaluation/design-review categories don't fit this project. Each
entry below is marked N/A with a one-line reason grounded in what the
codebase actually does (or deliberately doesn't do) — see
[`docs/DESIGN_REVIEW.md`](DESIGN_REVIEW.md) and
[`docs/ARCHITECTURE.md`](ARCHITECTURE.md) for the fuller picture behind
each.

| Category | Status | Why N/A |
|---|---|---|
| GPU utilization | N/A | Generation runs against the hosted Gemini API (`app/services/gemini_client.py`); the only local model is the small CPU-friendly `all-MiniLM-L6-v2` embedder (`embedding_service.py`), and `backend/Dockerfile` installs the CPU-only torch wheel specifically because no GPU is used or provisioned anywhere in this stack. |
| Agent handoff accuracy | N/A | Single-agent design — one `ChatService` dispatching to three tools (retrieval, summarization, web search), not multiple cooperating agents — so there's no handoff to measure. Web search is a hand-coded score-threshold decision, not an LLM-reasoned handoff to a second agent. See `docs/ARCHITECTURE.md`'s "Framework choice" section for why. |
| Weather / SQL / email / GitHub / speech tools | N/A | Out of scope for a document-QA product. The tool surface is retrieval and summarization over uploaded PDFs, plus a narrow web-search fallback for when retrieval alone doesn't confidently answer the question (`retrieval_service.py`, `summarization_service.py`, `web_search_service.py`), plus plant-disease image diagnosis via the LeafSense vision service (`vision_client.py`, `vision_qa_service.py` — see the Vision row below, genuinely implemented, not N/A) — not a general tool-use surface. Note: PDF text extraction (`document_service.py`) reads PyMuPDF's embedded/selectable text first and falls back to OCR (pytesseract/tesseract) only for pages with no text layer at all — see the README's Features section and Known Limitations for what that fallback does and doesn't cover. |
| Vision | **NOT N/A — implemented.** ✅ | Plant-disease image diagnosis is a real, tested tool: `POST /chat/diagnose(/stream)` → `vision_client.py::diagnose_image()` (calls the external LeafSense service) → `vision_qa_service.py` feeds the prediction back through the same RAG loop for treatment guidance. Measured on 4 synthetic robustness-test images in `eval/module10/reports/multimodal_eval_20260919T110330Z.json` (see `docs/MODULE10_FINAL_AUDIT.md` §8/22 for the honest scope caveat: robustness only, not diagnostic accuracy on real photos, since no real labeled photo corpus exists in this repo). This row exists only to correct an earlier, incorrect draft of this table that grouped Vision with genuinely-unimplemented tools (weather/SQL/email/GitHub) — that was a documentation error, not a design decision. |
| JWT | Resolved — see `docs/CHECKLIST.md` §13 | Individual user login now exists alongside the original API-key auth, not instead of it. `POST /auth/signup`/`POST /auth/login` (`app/api/v1/routes/auth.py`) create a `User` (bcrypt-hashed password) with its own personal `Tenant` (1:1 — the mechanism that makes per-user document/chat-history privacy free, since `Document`/`ChatSession` were already `tenant_id`-scoped) and return a JWT. `app/core/auth.py`'s `require_auth` checks `Authorization: Bearer <jwt>` first, falling through unchanged to the original `X-API-Key` path (`app/core/config.py:Settings.api_key_table`) if absent — both resolve to the same `request.state.{tenant_id,role}` shape, so RBAC/permissions/audit-logging/rate-limiting never needed to know which path fired. `X-API-Key` remains the right choice for non-browser/service clients (scripts, CI); JWT is what the web frontend uses now (`frontend/src/contexts/AuthContext.jsx`). The trigger predicted here — "multi-user access is needed" — is what actually happened; this row is now describing history, not a still-true absence. |
| RBAC | Resolved as of this migration — see `docs/CHECKLIST.md` §13 | A minimal admin/member role now exists (`Tenant.role`, `app/models/db_models.py`; `Settings.admin_client_names`, checked live per-request, not baked in at tenant creation), enforced through a central permission registry (`app/core/permissions.py`) rather than duplicated inline checks: a fixed permission vocabulary, an explicit role→permission map, and one `check_permission()` function, gating two actions today — `DELETE /documents/{id}` (mistake-prevention/access-control) and `GET /documents?all_tenants=true` (cross-tenant oversight visibility) — with the room to add a third as a 2-line registry change, not a new pattern. Deliberately not a large-scale multi-role permission/scope system (dynamic roles, per-resource ACLs) — the mechanism is now genuinely reusable, only the permission set stays small, proportionate to what this app actually does. Only takes effect when `DATABASE_URL` is set; without a DB there's nowhere to persist per-tenant role, so `document_delete` falls back to its pre-RBAC, ungated behavior (same graceful-degradation pattern tenant-scoping already uses), while `document_list_all_tenants` is denied outright since there's no pre-RBAC behavior to fall back to for a brand-new action — this asymmetry is explicit in the registry (`_DEGRADE_ALLOW_WHEN_NO_ROLE`), not implicit per call site. |
| Live cloud metrics (Prometheus/Grafana dashboards) | Partially resolved — see `docs/CHECKLIST.md` §12 | `GET /metrics` (`app/core/metrics.py`, `app/api/v1/routes/metrics.py`) now serves live, in-process metrics in Prometheus text-exposition format — any Prometheus/Grafana Cloud agent can scrape it directly. No hosted dashboard stack of our own is built on top of it, and there's no CloudWatch or other managed-cloud metrics integration (no cloud deployment currently runs this app). `backend/eval/metrics_report.py` remains the offline, log-parsing counterpart. |
| Rate limiting (advanced) | N/A (future work) | Basic per-key in-memory rate limiting (60 req/min sliding window) is now implemented in `app/core/auth.py`. A production-grade token bucket with persistence, distributed enforcement, and configurable tiers remains future work. |
